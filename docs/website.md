# Website ownership and delivery

The website is a private pnpm workspace. The root publishes the library/CLI; the website depends on that workspace and builds it first. Protocol 0.1 remains provisional independently of package availability.

## One content owner

website/src/site.config.ts owns the nine canonical page records. The layout emits metadata through jg-personal-astro-ui's DocumentHead and jg-site. Sitemap, robots.txt, llms.txt, navigation, and Markdown alternatives derive from those records. The real 404 is noindex and omitted from discovery.

The protocol, getting-started, API, CLI, integration, and example guides render their canonical Markdown files. website/src/content/sources.ts explicitly registers the public inputs. It never discovers planning roots, private plans, instruction files, or history. The gallery computes observations through jg-plans at build time; no browser parser or service is introduced. Visual guides pair Markdown with selected JSON result fields before the complete references. Markdown comes first in reading and visual order at every viewport, including the expanded revision example; document-flow pairs stack below 1024px and use two columns from 1024px. The shared documentation shell, outline and page navigation retain the registered routes and source actions, while the document-title scale preserves the existing title and reference IDs. CodeBlock owns the wrapped 23rem document-flow bodies and icon-only copy controls; the Markdown plugin uses the same display option. Shared tab enhancement replaces the local no-JavaScript fallback without changing raw-page navigation. Sample links open readable Markdown. Direct download endpoints match the source files byte-for-byte. Raw Markdown adds availability context without replacing the canonical content.

The homepage and examples page share a create → inspect → update → revise walkthrough on the protocol 0.2 criteria example. website/scripts/lifecycle/ runs the public filesystem API in an owned temporary directory and removes it after collecting deterministic public observations. Its concise body is website-owned; metadata and milestone identities come from the registered public example. The update view shows each criterion's derived progress. The revision adds AC-04, compares the actual documents with the shared CodeDiff, retains exact milestone bytes, shows the example consumer binding becoming stale and shows check's real UNASSIGNED_CRITERION finding. A repeated update with the pre-revision hash records the real JG_PLANS_SOURCE_CHANGED refusal for the homepage's guarded-write steps. This demonstrates document operations without inventing completion evidence or approval. API excerpts and the full revised Markdown remain copyable.

The homepage dashboard renders the criteria example's milestones and criterion progress, and the check report marks each finding checkPlan reports for the registered criteria-invalid example on its own line. Both are computed at build time; the invalid example stays out of the gallery.

Plain Markdown destinations do not opt into native page transitions. The base layout explicitly skips the outgoing transition for /raw/ links through pageswap, while HTML page transitions keep the shared UI behavior. Browsers without that optional event still navigate normally. The layout also repeats the shared opt-in and its reduced-motion opt-out in an inline head style, because Chromium can resolve an incoming page's opt-in before the bundled stylesheet is active, which skips the transition and reports an unhandled InvalidStateError. See [cross-document transition controls](https://developer.chrome.com/docs/web-platform/view-transitions/cross-document).

## Availability is evidence

Offline local builds show development preview. With JG_PLANS_PUBLISHED_VERSION, the build first requires the requested version to match the root source version, then compares the downloadable npm archive's complete paths/content hashes with a fresh pack of the built source. A match permits an exact-version install action. Missing/pending releases, differing contents, and unavailable registry evidence suppress it. A registry error never proves absence.

Package availability belongs beside installation instructions and in documentation metadata, not in a site-wide banner. Verified documentation links name the npm version; unverified documentation identifies a development preview or unavailable evidence. Protocol maturity remains separate from package availability.

The build wrapper owns verification and overwrites the internal presentation input passed to Astro. No alternate registry is exposed through its command or environment. Integration tests exercise real bounded HTTP fixtures and disposable release/unknown builds; those artifacts are never deployed. release.json records the checked artifact's version, state, provisional protocol, and CI source commit.

Cloudflare can mistake a versioned package specifier for an email address. The install component is enclosed in its documented email_off HTML comments, preserved through the production build, so the edge leaves the command intact. Cloudflare consumes the two control comments when serving it. For the published homepage only, live verification accepts the original bytes or the exact artifact with that single matched pair removed. It derives that expected response from the retained artifact, never normalizes received HTML, and rejects every other difference. Other files, source downloads and the custom 404 remain byte-exact. See [Cloudflare's obfuscation exclusions](https://developers.cloudflare.com/waf/tools/scrape-shield/email-address-obfuscation/#prevent-cloudflare-from-obfuscating-email).

## Checked artifact to Pages

Check verifies the package, six runtime combinations, and the website. The website job uploads the unchanged tested dist as qualified-site and, on main, as the Pages artifact. Deployment depends on package/runtime/website checks, with no dependency or condition on the publish job. A disabled, skipped, or failed npm publication does not cancel an otherwise eligible Pages deployment. Main deployments are not cancelled by later runs.

The existing github-pages environment allows main. The deployment job uses job-local Pages/OIDC permissions, deploys the artifact, then compares live HTTPS bytes with qualified-site and verifies that unknown routes return the checked custom 404. No label or file is edited between checking and deployment. Keep a successful qualified-site artifact for rollback; redeploy it rather than silently rebuilding another tree.

After npm publication is verified, manually run Check on main with published_version set to that tree's matching package version. It produces and checks a fresh release-mode artifact before deployment. Setting npm readiness alone does not refresh a site's existing presentation.

Browser checks cover all pages, including the custom 404, in both themes at 320px/tablet/desktop, WCAG 2.2 AA, keyboard/focus, Markdown-to-JSON examples, icon-only copy success/failure, readable source links, absence of download controls, no JavaScript, zoom, and reduced motion.
